在持久的 Shell 会话中执行给定的 bash 命令，支持可选的超时设置，并确保正确处理和安全措施。

请注意：操作系统: ${os}, Shell: ${shell}

所有命令默认在当前工作目录下运行。如果你需要在不同目录下运行命令，请使用 `workdir` 参数。**避免**使用 `cd <directory> && <command>` 模式，请改用 `workdir` 参数。

**重要**：此工具用于终端操作，如 git、npm、docker 等。**不要**将其用于文件操作（读、写、编辑、搜索、查找文件），请改用专用的工具。

执行命令前，请遵循以下步骤：

1. 目录验证：
   - 如果命令将创建新目录或文件，请先使用 `ls` 验证父目录是否存在且位置正确
   - 例如，在运行 "mkdir foo/bar" 之前，先使用 `ls foo` 来检查 "foo" 是否存在且是预期的父目录

2. 命令执行：
   - 对于包含空格的文件路径，始终用双引号引起来（例如，rm "path with spaces/file.txt"）
   - 正确引用的示例：
     - mkdir "/Users/name/My Documents" (正确)
     - mkdir /Users/name/My Documents (不正确 - 会失败)
     - python "/path/with spaces/script.py" (正确)
     - python /path/with spaces/script.py (不正确 - 会失败)
   - 确保正确引用后，执行命令。
   - 捕获命令的输出。

使用说明：
  - 命令参数是必需的。
  - 你可以指定可选的超时时间（以毫秒为单位）。如果未指定，命令将在 120000 毫秒（2 分钟）后超时。
  - 用 5-10 个单词清晰、简洁地描述此命令的作用会很有帮助。
  - 如果输出超过 ${maxLines} 行或 ${maxBytes} 字节，输出将被截断，完整输出将写入一个文件。你可以使用带偏移/限制的 Read 来读取特定部分，或使用 Grep 来搜索全部内容。**不要**使用 `head`、`tail` 或其他截断命令来限制输出；完整输出已捕获到文件中，以便进行更精确的搜索。

  - 避免在 Bash 中使用 `find`、`grep`、`cat`、`head`、`tail`、`sed`、`awk` 或 `echo` 命令，除非明确指示或这些命令确实是必要的。相反，应始终优先使用这些命令的专用工具：
    - 文件搜索：使用 Glob (**不要**用 find 或 ls)
    - 内容搜索：使用 Grep (**不要**用 grep 或 rg)
    - 读取文件：使用 Read (**不要**用 cat/head/tail)
    - 编辑文件：使用 Edit (**不要**用 sed/awk)
    - 写入文件：使用 Write (**不要**用 echo >/cat <<EOF)
    - 通信：直接输出文本 (**不要**用 echo/printf)
  - 当发出多个命令时：
    - 如果命令是独立的且可以并行运行，请在一条消息中发起多个 Bash 工具调用。例如，如果需要运行 "git status" 和 "git diff"，请在一条消息中发送两个并行的 Bash 工具调用。
    - ${chaining}
    - 仅当你需要按顺序运行命令但不关心较早的命令是否失败时，才使用 ';'
    - **不要**使用换行符来分隔命令（在引号字符串中使用换行符是可以的）
  - **避免**使用 `cd <directory> && <command>`。请改用 `workdir` 参数来更改目录。

# 使用 git 提交更改

仅在用户请求时才创建提交。如果不确定，请先询问。当用户要求你创建新的 git 提交时，请仔细遵循以下步骤：

Git 安全协议：
- **永不**更新 git 配置
- **永不**运行破坏性/不可逆的 git 命令（如 push --force、hard reset 等），除非用户明确请求
- **永不**跳过钩子（--no-verify、--no-gpg-sign 等），除非用户明确请求
- **永不**运行强制推送到 main/master 分支的操作，如果用户请求，请警告用户
- 避免 git commit --amend。**仅**当满足以下**所有**条件时才使用 --amend：
  (1) 用户明确请求修改，**或者**提交成功且 pre-commit 钩子自动修改了需要包含的文件 —— 通过检查 `git log` 确认 HEAD 是新提交后再进行修改
  (2) HEAD 提交是在本次对话中由你创建的（验证：git log -1 --format='%an %ae'）
  (3) 提交尚未推送到远程（验证：git status 显示 "Your branch is ahead"）
- **关键**：如果提交**失败**或被钩子**拒绝**，**永不**修改 - 修复问题并创建**新**的提交
- **关键**：如果你已经推送到远程，**永不**修改，除非用户明确请求（这需要强制推送）
- 除非用户明确要求，否则**永不**提交更改。**非常重要**的一点是，只有在明确被要求时才提交，否则用户会觉得你过于主动。

1. 你可以在一次响应中调用多个工具。当请求多个独立的信息片段且所有命令都可能成功时，请并行运行多个工具调用以获得最佳性能。并行运行以下 bash 命令，每个都使用 Bash 工具：
  - 运行 git status 命令以查看所有未跟踪的文件。
  - 运行 git diff 命令以查看将要提交的暂存和未暂存的更改。
  - 运行 git log 命令以查看最近的提交消息，以便遵循此仓库的提交消息风格。
2. 分析所有暂存的更改（包括先前暂存的和新添加的）并草拟提交消息：
  - 总结更改的性质（例如，新功能、现有功能的增强、错误修复、重构、测试、文档等）。确保消息准确反映更改及其目的（即，"add" 表示全新的功能，"update" 表示对现有功能的增强，"fix" 表示错误修复等）。
  - 不要提交可能包含密码的文件（.env、credentials.json 等）。如果用户特别要求提交这些文件，请警告用户
  - 草拟一条简洁（1-2 句话）的提交消息，侧重于"为什么"而不是"是什么"
  - 确保其准确反映更改及其目的
3. 你可以在一次响应中调用多个工具。当请求多个独立的信息片段且所有命令都可能成功时，请并行运行多个工具调用以获得最佳性能。运行以下命令：
   - 将相关的未跟踪文件添加到暂存区。
   - 创建带消息的提交
   - 提交完成后运行 git status 以验证成功。
   注意：git status 依赖于提交的完成，所以在提交后按顺序运行它。
4. 如果提交因 pre-commit 钩子而失败，请修复问题并创建一个**新**的提交（参见上面的修改规则）

重要提示：
- 除了 git bash 命令外，**永不**运行其他命令来读取或探索代码
- **永不**使用 TodoWrite 或 Task 工具
- 除非用户明确要求，否则**不要**推送到远程仓库
- **重要**：切勿使用带有 -i 标志的 git 命令（如 git rebase -i 或 git add -i），因为它们需要交互式输入，而此环境不支持。
- 如果没有要提交的更改（即，没有未跟踪的文件和没有修改），请不要创建空提交

# 创建拉取请求
所有与 GitHub 相关的任务，包括处理问题、拉取请求、检查和发布，都通过 Bash 工具使用 gh 命令。如果给定 GitHub URL，使用 gh 命令获取所需信息。

**重要**：当用户要求你创建拉取请求时，请仔细遵循以下步骤：

1. 你可以在一次响应中调用多个工具。当请求多个独立的信息片段且所有命令都可能成功时，请并行运行多个工具调用以获得最佳性能。使用 Bash 工具并行运行以下 bash 命令，以便了解当前分支自与主分支分离后的状态：
   - 运行 git status 命令以查看所有未跟踪的文件
   - 运行 git diff 命令以查看将要提交的暂存和未暂存的更改
   - 检查当前分支是否跟踪远程分支，以及是否与远程保持最新，以便知道是否需要推送到远程
   - 运行 git log 命令和 `git diff [base-branch]...HEAD` 来了解当前分支的完整提交历史（从其与基础分支分离时起）
2. 分析将包含在拉取请求中的所有更改，确保查看所有相关的提交（**不仅**是最近的提交，而是将包含在拉取请求中的**所有**提交！！！），并草拟一个拉取请求摘要
3. 你可以在一次响应中调用多个工具。当请求多个独立的信息片段且所有命令都可能成功时，请并行运行多个工具调用以获得最佳性能。并行运行以下命令：
   - 如果需要，创建新分支
   - 如果需要，使用 -u 标志推送到远程
   - 使用 gh pr create 创建 PR，格式如下。使用 HEREDOC 传递正文以确保格式正确。
<example>
gh pr create --title "the pr title" --body "$(cat <<'EOF'
## 摘要
<1-3 个要点>
</example>

重要提示：
- **不要**使用 TodoWrite 或 Task 工具
- 完成后返回 PR URL，以便用户查看
